# Entities

Entities map to tables.

```jwc
entity User of AppDb {
    id         int pk autoincrement;   // primary key, auto-increment
    name       varchar(120);
    email      varchar(255) unique;
    age        int nullable;           // nullable
    created_at datetime;
}
```

Column declarations are `<name> <type> <modifiers...>;` — **no colon** between
the name and type (a `name:` form is reserved for [navigation
properties](#navigation-properties)). Entity column types are SQL types
(`int`, `bigint`, `varchar(n)`, `text`, `datetime`, `uuid`, `bool`, `json`,
`decimal(p,s)`, `bytea`) — `string` is for `class` DTOs, not entity columns.

`of <dbcontext>` ties the entity to a connection. If omitted, falls back to the single dbcontext in the program (error if there are multiple).

## Field modifiers

| Modifier | Meaning |
|---|---|
| `pk` | Primary key (single column). |
| `autoincrement` | Auto-increment — Postgres `GENERATED BY DEFAULT AS IDENTITY`. Aliases: `auto_increment`, `serial`. |
| `unique` | `UNIQUE` constraint on the column. |
| `nullable` | Column allows `NULL` (columns are `NOT NULL` by default). |
| `references <Entity>.<col> [on delete ...]` | Foreign key — see below. |

Modifiers are bare keywords after the type, e.g. `email varchar(255) unique nullable;`. Column-level `default` values and composite primary keys (`pk on (a, b)`) are **not implemented yet** for entity columns.

## Foreign keys

```jwc
entity Post of AppDb {
    id      int pk autoincrement;
    user_id uuid references User.id on delete cascade;
    title   varchar(200);
}
```

Supported actions: `cascade`, `restrict`, `set null`.

## Navigation properties

Navs use the `name: Type via ...` form (note the colon — that's what
distinguishes them from columns). They declare in-language relations so
[`select ... with`](./select.md#with--eager-nav-loading) fetches them as
nested JSON in one query — no N+1. The `via` shape picks the relation kind:

```jwc
entity Post of AppDb {
    id        int pk autoincrement;
    userId    int;
    authorId  int;
    createdAt datetime;

    // belongs-to / has-one: a BARE via column on THIS entity holds the FK.
    author: User via authorId;

    // has-many: a DOTTED via points at the FK column on the TARGET entity.
    comments: List<Comment> via Comment.postId orderby createdAt desc;

    // many-to-many: via a link table — via JoinTable(nearCol, farCol).
    tags: List<Tag> via PostTag(postId, tagId);
}
```

| `via` form | Relation | Materialises as |
|---|---|---|
| `via localFk` (bare) | belongs-to / has-one | nested object |
| `via Target.fk` (dotted) | has-many / has-one | array / object |
| `via JoinTable(near, far)` | many-to-many | array |

Extras:

- **Projection** — `assignees: List<User> { id, name } via ...` materialises
  only those columns, so secrets like `passwordHash` never leak.
- **Ordering** — `orderby <col> [asc|desc]` (as above) makes a collection
  deterministic.
- **Nesting** — load two levels at once with a dotted `with`:
  `select Project with boards.columns ...` (see
  [select](./select.md#with--eager-nav-loading)).

```jwc
let posts = select Post with author, comments, tags from AppDb.Post;
```

Each nav emits one correlated `json_agg(...)` / `row_to_json(...)` subquery.

## Generated SQL

```bash
jwc gen-sql models/User.jwc     # → CREATE TABLE "users" (...);
```

Use [`jwc migrate new`](./migrations) to capture schema changes as migration files instead of dumping raw DDL.
