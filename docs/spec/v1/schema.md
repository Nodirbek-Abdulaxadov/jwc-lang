# schema.md — tables, enums, constraints, indexes, and generated DDL

Normative. This document is the **DBA test**: a Postgres engineer reading a
`table` declaration and this file can state the exact DDL, without asking.

Closes **N1** (`on update now()`), **N10** (`identity` physical form, doc
comments), and gaps **#23**, **#25**, **#28**, **#30**, **#33**, **#35**.

---

## 1. Objects

A JWC program declares five classes of database object. All five are
snapshotted and diffed (migrations §2).

| Declaration | DDL object |
|---|---|
| `schema s of App;` | `CREATE SCHEMA` |
| `enum E of App.s { … }` | `CREATE TYPE … AS ENUM` |
| `table T of App.s { … }` | `CREATE TABLE`, its constraints |
| `index on (…)` inside a table | `CREATE INDEX` / `CREATE UNIQUE INDEX` |
| `col … on update now()` | `CREATE FUNCTION` + `CREATE TRIGGER` |
| `--- doc` | `COMMENT ON` |
| `view V of App.s { … }` | `CREATE VIEW` — **not in 0.22.0** (queries §8) |

## 2. Columns

```
column_def = ident type_ref [ modifiers ] ";"
```

### 2.1 NOT NULL by default

A column declared `col T` is `NOT NULL`. A column declared `col T?` is
nullable. There is no other spelling.

### 2.2 Modifiers

| Modifier | Effect |
|---|---|
| `primary key` | single-column PK (§4.1) |
| `identity` | `GENERATED BY DEFAULT AS IDENTITY` (§2.3) |
| `unique` | single-column unique constraint (§4.3) |
| `unique : "msg"` | same, plus a promoted error message (errors §6) |
| `private` | never in a response, never accepted from a body (§3.1) |
| `server` | never accepted from a body; appears in responses (§3.2) |
| `default expr` | column `DEFAULT` (§2.4) |
| `on update now()` | trigger-maintained (§6) |
| `as "name"` | physical name override (names §4.2) |
| `was "name"` | declared rename (migrations §6) |
| `minLength(n)`, `pattern(r"…")`, `min(n)`, `max(n)`, `oneOf(…)` | `CHECK` constraint (§4.4) |

Modifiers may be separated by whitespace or by commas; both parse
identically. `varchar(255) private, unique` and `varchar(255) private unique`
are the same declaration.

### 2.3 `identity` (N10)

`bigint primary key identity` emits:

```sql
id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Not `bigserial`. Reasons, stated because the DBA test requires them: an
identity column owns its sequence (dropping the table drops it), `BY DEFAULT`
permits explicit inserts (which seeding and migration backfills need), and
the form is SQL-standard. `identity` on a non-integer type is `E0401`.

### 2.4 `default`

The expression must be a literal, an enum member, or one of the
Postgres-side calls `now()`, `gen_random_uuid()`, `''`, `'{}'`. It is
evaluated **by Postgres**, not by the application (types §2.4). Any other
expression is `E0402`.

`default now()` on a non-temporal column is `E0403`.

## 3. `private` and `server` (#35)

### 3.1 `private`

A `private` column:

- is **excluded from the raw path**. A `select` with no `as { }` against a
  table that has any `private` column does not emit `row_to_json(t)`; it
  emits an explicit column list built from the non-private columns
  (queries §7.2). This is the clause that makes "raw by default" and
  "`private` is never in a response" both true at once.
- may not appear in an `as { }` projection (`E0410`).
- may not appear in a `view` body (`E0410`).
- may not be the target of a spread (types §9.4).
- **may** appear in a `where`, `on`, `having` or `set` expression. Comparing
  against a hash is the entire point of storing one.

### 3.2 `server`

A `server` column may not be written by a spread and may not appear in a
`class` (types §9.4), but is visible in projections and on the raw path. It
is for values the server assigns: `invited_by`, `created_by`.

### 3.3 Interaction with `view`

A view whose body names a `private` column is `E0410` at the view's
declaration site, not at its use site.

## 4. Constraints

### 4.1 Primary key

Column form: `id bigint primary key identity;`
Table form: `primary key (org_id, account_id);`

Both forms in one table is `E0420`. Zero PKs is `W0401` — legal (log tables),
warned because `first`, `update … first` and keyset pagination all need one
(queries §5.4).

### 4.2 Foreign key

```
foreign key (org_id) references App.org.Orgs (id) on delete cascade;
foreign key (org_id, account_id) references App.org.Members (org_id, account_id);
```

- Column counts must match (`E0421`).
- The referenced columns must be a declared PK or unique constraint of the
  target (`E0422`) — Postgres requires it and saying so at compile time
  turns a deploy failure into an edit.
- `on delete` / `on update` actions: `cascade`, `restrict`, `no action`,
  `set null`, `set default`. Default is `no action`.
- `set null` on a `NOT NULL` column is `E0423`.
- A composite FK is written as **one** constraint, not per column. Splitting
  it changes its meaning: two single-column FKs permit a `(org_a, user_b)`
  pair that exists in neither combination.
- An FK carries **no message**. FK violations map to `BadRequest` 400 by
  default (errors §6.3); per-FK messages are `DEFERRED-4`.

### 4.3 Unique

```
unique (org_id, key) : "message";
unique (org_id) where status != SubscriptionStatus.canceled : "message";
```

A `unique` with **no** `where` becomes a table `UNIQUE` constraint. A
`unique` **with** a `where` becomes `CREATE UNIQUE INDEX … WHERE` — Postgres
has no partial unique *constraint* (#25).

The predicate is canonicalised at compile time before it reaches DDL, so the
same source predicate always produces the same index and the migration diff
can compare predicates textually:

| Source | Canonical SQL |
|---|---|
| `x == null` | `x IS NULL` |
| `x != null` | `x IS NOT NULL` |
| `status != SubscriptionStatus.canceled` | `status <> 'canceled'` |
| `a and b` | `(a) AND (b)` |
| `!a` | `NOT (a)` |

Canonicalisation orders `AND`/`OR` operands by their canonical text, so
`a and b` and `b and a` produce the same index — and therefore no spurious
migration.

### 4.4 Check

Column rules and table `check` both become `CHECK` constraints:

| Written | Emitted |
|---|---|
| `title varchar(200) minLength(1);` | `CHECK (char_length(title) >= 1)` |
| `email varchar(255) pattern(r"…");` | `CHECK (email ~ '…')` |
| `price_cents int min(0);` | `CHECK (price_cents >= 0)` |
| `check (a > b) : "msg";` | `CHECK ((a) > (b))` |

A rule on a nullable column is emitted as `CHECK (col IS NULL OR …)`, so a
`NULL` never violates a length or pattern rule.

`check` expressions may reference only columns of their own table, literals,
enum members and the operators of types §12. A function call other than the
canonical set (`char_length`, `~`, `lower`, `upper`) is `E0424`.

### 4.5 `index ... using <method>`

The access method is passed through to Postgres. It must be one it has —
`btree` (the default), `hash`, `gin`, `gist`, `brin`, `spgist` — otherwise
`E0431`.

One compatibility rule is checked, because it is the mistake people actually
make: **`using gin` on a plain `varchar`/`text` column is `E0431`.** GIN
indexes an array, `jsonb` or `tsvector` out of the box; on a text column it
needs `gin_trgm_ops` from the `pg_trgm` extension, and JWC does not create
extensions. The diagnostic says so and points at writing that index by hand.

No other operator-class compatibility is checked. The full matrix is large
and changes per Postgres release; an unsupported combination fails at apply
time with Postgres's own hint, which is a clear message on the migration
that introduced it.

## 5. Enums

### 5.1 `enum E { a, b }` — no `of`

No type is created. A column of type `E` is `varchar(n)` where `n` is the
longest member's length, plus:

```sql
CHECK (col IN ('a','b'))
```

named `ck_<table>__<col>__enum`.

### 5.2 `enum E of App.s { a, b }`

```sql
CREATE TYPE s.e AS ENUM ('a', 'b');
```

Columns use the type directly. Evolution is constrained: `ADD VALUE` cannot
run inside a transaction block, so migrations that add a value are emitted
in their own non-transactional file (migrations §5). `DROP VALUE` does not
exist in Postgres and is `DEFERRED-3`.

### 5.3 Choosing

The `of`-less form is cheaper to evolve; the `of` form is a real type a DBA
can see in `\dT`. The language does not choose for you. Both are shown in
the sample.

## 6. `on update now()` (N1)

Postgres has no `ON UPDATE` clause. `updated_at timestamptz default now() on
update now();` emits a per-table trigger:

```sql
CREATE OR REPLACE FUNCTION billing.tg_subscriptions__touch()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END $$;

CREATE TRIGGER tg_subscriptions__touch
BEFORE UPDATE ON billing.subscriptions
FOR EACH ROW EXECUTE FUNCTION billing.tg_subscriptions__touch();
```

Rules:

- One function and one trigger per table, regardless of how many columns
  carry `on update`. The body assigns each of them.
- The only permitted expression is `now()` (`E0430` otherwise). A general
  expression here would be a stored procedure language, which is out of
  scope.
- Function and trigger are snapshotted objects and participate in the diff
  (migrations §2). Dropping the last `on update` column drops both.

## 7. Doc comments → `COMMENT ON` (N10)

```jwc
--- Tenant. One row per paying organisation.
table Orgs of App.org {
    --- URL-safe handle, immutable after creation.
    slug varchar(40) unique : "bu slug band";
}
```

```sql
COMMENT ON TABLE  org.orgs      IS 'Tenant. One row per paying organisation.';
COMMENT ON COLUMN org.orgs.slug IS 'URL-safe handle, immutable after creation.';
```

Multi-line doc blocks join with `\n`. Comments are diffed: changing the text
emits a `COMMENT ON` in the next migration and nothing else.

## 8. Constraint and index naming (#28, #30)

Names are **generated, deterministic, versioned, and always written
explicitly in the DDL**. No name is ever left to Postgres, because the
runtime maps a violated constraint back to its message by name (errors §6).

### 8.1 The function — `v1`

Let `t` = physical table name, `c` = physical column names joined by `_`,
`h(x)` = the first 8 lowercase hex digits of SHA-256 over the canonical
predicate text (§4.3).

| Object | Name |
|---|---|
| primary key | `pk_<t>` |
| unique constraint | `uq_<t>__<c>` |
| partial unique index | `uq_<t>__<c>__<h(pred)>` |
| foreign key | `fk_<t>__<c>` |
| check (table form, `n`th on the table) | `ck_<t>__<c>__<n>` |
| check (column rule) | `ck_<t>__<c>__<rule>` |
| index | `ix_<t>__<c>` |
| partial index | `ix_<t>__<c>__<h(pred)>` |
| enum CHECK | `ck_<t>__<c>__enum` |
| touch trigger + function | `tg_<t>__touch` |

If a name exceeds Postgres's 63-byte limit, the *column* segment is replaced
by `h(columns)` and the name is re-formed. Truncation is never used: two
truncated names can collide.

### 8.2 Versioned

The scheme is `v1`. A future scheme is `v2` and both are understood by the
migration engine, which records the scheme in the snapshot. A generator
change never silently renames a live constraint.

### 8.3 Independent of the message (#28)

The name is derived from table + columns + predicate only. Editing a
constraint's message text changes **no DDL** and produces **no migration**;
it changes only the compiled message table. This is the fix for the
name↔message coupling gap: they were coupled because the name embedded
nothing stable, and the message was matched by name at runtime.

## 9. Emission order (#33)

`jwc gen-sql` emits in exactly this order, and each phase is sorted
deterministically (by schema name, then object name):

1. `CREATE SCHEMA IF NOT EXISTS` — every declared schema
2. `CREATE TYPE … AS ENUM` — every `of` enum
3. `CREATE TABLE` — columns, PK, CHECK, and **column-level UNIQUE** only
4. `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY` — **every FK, all of them,
   in one pass after every table exists**
5. `CREATE UNIQUE INDEX` / `CREATE INDEX`
6. `CREATE FUNCTION` + `CREATE TRIGGER`
7. `CREATE VIEW` — after every table it reads, and after any view **it**
   reads (queries §8.2). `CREATE VIEW` resolves its source at creation
   time, so this order is not cosmetic: the wrong one fails to apply.
8. `COMMENT ON`

Phase 4 is why cross-schema FK cycles work. The sample has one
(`auth → org → auth`) and no per-file ordering can resolve it; a separate
pass makes the question disappear rather than answering it.

Within a phase, order is total and stable, so two runs of `jwc gen-sql` on
the same source are byte-identical (`tests/ddl_golden/`).

### 9.1 `--explain`

`jwc gen-sql --explain` prefixes each statement with a comment naming the
source:

```sql
-- src/db/billing.jwc:48
CREATE UNIQUE INDEX uq_subscriptions__org_id__1f4c9ab2
    ON billing.subscriptions (org_id)
    WHERE status <> 'canceled';
```

Every statement carries one. A statement with no source location is a
compiler bug and fails the golden test.

## 10. `NOT NULL ADD COLUMN` policy (#23)

Adding a `NOT NULL` column with no `default` to a table that may hold rows
is **refused at generation time** (`E0440`), with the expand/contract recipe
printed:

```
E0440: adding NOT NULL column `org.orgs.region` with no default
  A NOT NULL column cannot be added to a table that may hold rows.
  Either:
    1. give it a default:          region varchar(20) default "us";
    2. or make it nullable now and tighten later (expand/contract):
         migration 1:  region varchar(20)?              -- add, backfill
         migration 2:  region varchar(20)               -- SET NOT NULL
```

The generator does not consult the live database to decide (`migrate new`
runs offline). "May hold rows" means "the table is not being created by this
same migration".

## 11. Diagnostics introduced here

| Code | Meaning |
|---|---|
| `E0401` | `identity` on a non-integer column |
| `E0402` | non-constant `default` |
| `E0403` | `default now()` on a non-temporal column |
| `E0410` | `private` column in a projection or view |
| `E0420` | both column-level and table-level primary key |
| `E0421` | FK column count mismatch |
| `E0422` | FK target is not a PK or unique |
| `E0423` | `on delete set null` on a `NOT NULL` column |
| `E0424` | unsupported function in a `check` |
| `E0430` | `on update` expression other than `now()` |
| `E0431` | unknown index access method, or GIN on a scalar |
| `E0450` | unknown schema |
| `E0451` | index or constraint names a column the table does not have |
| `E0452` | `required` used as a column modifier |
| `E0453` | unknown column rule |
| `E0440` | `NOT NULL` column added with no default |
| `W0401` | table has no primary key |
